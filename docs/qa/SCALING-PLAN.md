# План масштабирования: 100 → 1 000 000 пользователей

Опирается на замеры прода 14.09 (Infinity QA, циклы 1–5). Решение владельца на
14.09: сервер не меняем, выжимаем текущий VPS; всё про больший сервер — план.

## Исходная точка (замер 14.09)

| Ресурс | Значение |
|---|---|
| VPS | 1 ядро, 961 МБ RAM, своп 2 ГБ (занято ~890 МБ), общий с чужим проектом |
| Память сервисов | youtube-user 182 МБ, worker 142 МБ, api 129 МБ, bot 15 МБ, redis 3 МБ |
| БД | SQLite WAL, 13.7 МБ, 7.4 тыс. треков |
| API прогретый | `/library/ids` 5 мс, `/tracks?100` 66 мс, `/profile` 122 мс, `/mix` 82 мс |
| Аудио | файл 7 МБ целиком 19 мс; 8 параллельных потоков +12 МБ RSS |
| Локально под нагрузкой | 300 параллельных `/library/ids`: p50 1.1 сек, p95 1.7 сек, 0 ошибок |
| Ошибки | 0 за сутки в журналах, 0 ответов 5xx |

Узкие места по порядку, в котором упрёмся: **CPU одного ядра** (yt-dlp, ffmpeg,
Python-интерпретаторы) → **единственный писатель SQLite** → **RAM** (своп уже
занят) → **исходящий трафик аудио**.

## 100 пользователей — сейчас, текущий VPS

Готово. Сделанное в циклах 1–5 и есть этот уровень:
- аудио с диска кусками, одна закачка на трек;
- лимитер по пользователю;
- кэш вердикта подписки;
- `ensure_user` без записи на каждое действие;
- Redis с потолком;
- тревоги об ошибках, откат деплоя.

## 1 000 пользователей — текущий VPS, без денег

| Что | Зачем | Эффект |
|---|---|---|
| Прогрев кэша страниц SQLite после рестарта | первый запрос 4.3 сек | холодный старт → десятки мс |
| Ночной нагрузочный тест прода (окно владельца) | реальный потолок RPS неизвестен | число вместо догадки |
| Аудио отдаёт nginx (`X-Accel-Redirect` на файл кэша) | сейчас байты гонит Python | CPU на поток ≈ 0, uvicorn свободен для API |
| Сборка Mini App в 1–3 файла | 46 модулей = десятки запросов | старт быстрее на мобильной сети |
| `Cache-Control` на неизменяемые ответы | уже на `/genres`, `/artists` | меньше запросов на открытие |

## 10 000 пользователей — VPS 2 ядра / 4 ГБ (~1–2 тыс. ₽/мес)

| Что | Зачем |
|---|---|
| **PostgreSQL вместо SQLite** | параллельная запись; `ILIKE` по кириллице работает сам; готовая строка `asyncpg` в requirements |
| uvicorn `--workers 2` | ⚠️ лимитер и кэши в памяти станут на процесс — перенести в Redis (INCR + TTL) |
| Поиск: PostgreSQL `pg_trgm` или SQLite FTS5 | `ilike '%q%'` — полный скан; на 7 тыс. незаметно, на 100 тыс. — сотни мс |
| youtube-user и worker на отдельные процессы с лимитом CPU (`CPUQuota`) | закачки не должны отнимать ядро у API и бота |
| Бэкап БД вне сервера | сейчас снимки на том же диске — не переживут потерю VPS |

## 100 000 пользователей — два сервера

| Что | Зачем |
|---|---|
| **Сервер A**: бот + API + PostgreSQL + Redis | отзывчивость |
| **Сервер B**: Celery-воркеры (yt-dlp, ffmpeg, минт) | тяжёлое не мешает людям |
| Аудио-кэш в S3-совместимом хранилище + CDN | трафик аудио — главный счёт; код хранилища S3 уже есть (`app/storage/s3.py`) |
| Бот на webhook вместо polling | меньше задержка и нагрузка, горизонтально масштабируется |
| Метрики (Prometheus/Grafana или хотя бы счётчики в Redis) | сторож видит «упало», но не «медленнее на 30%» |

## 1 000 000 пользователей

| Что | Зачем |
|---|---|
| API и бот за балансировщиком, 2+ экземпляра | отказоустойчивость, деплой без простоя |
| PostgreSQL с репликой на чтение | каталог и поиск читают, пишут библиотека и события |
| `track_events` — партиционирование по месяцам или вынос в ClickHouse | самая быстрорастущая таблица: миллионы прослушиваний в день |
| Очередь закачек с приоритетами и дедупликацией по треку | всплеск популярного трека не должен занять всех воркеров |
| Прогрев популярного каталога заранее (`cli/warmup.py` уже есть) | мгновенная выдача по `file_id` вместо закачки |
| Лимиты Telegram Bot API (~30 сообщений/сек на бота) | рассылки и выдача через очередь с темпом, несколько ботов-минтеров |

## Правило

Каждый шаг — сначала замер, потом переезд. Переходить на следующий уровень, когда
сторож или замер показывают упор (p95 API > 500 мс, свободная память < 100 МБ
дольше часа, очередь закачек не убывает), а не заранее.
