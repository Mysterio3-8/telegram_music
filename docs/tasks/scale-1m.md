# Масштаб на 1 млн пользователей

**Заведено:** 19.08.2026. **Статус:** оценка + план, железа нет.
Читать с [новая-машина.md](новая-машина.md) (что включить сразу после переезда) и
[growth.md](growth.md) (как этих пользователей набрать).

Владелец попросил «масштабировать на 1 млн активных в один момент». Ниже — что
это значит в цифрах, где нынешняя машина ломается (по реальным замерам, а не по
синтетическому флуду живого прода), и какая архитектура нужна.

---

## Сначала о числах: «1 млн активных в один момент» ≠ «1 млн пользователей»

Это разные задачи, и путать их дорого.

- **1 млн зарегистрированных** — цель роста. Реалистично планировать.
- **1 млн онлайн одновременно** — это уровень пиковой нагрузки крупного
  стримингового сервиса. Даже у ботов-миллионников одновременно активны единицы
  процентов аудитории. При 1 млн пользователей пик — это ~10–50 тысяч
  одновременных запросов, а не миллион.

Дальше считаю по реалистичному пику: **1 млн зарегистрированных, ~20–50 тыс.
запросов в пиковую минуту**. Если действительно нужен миллион одновременных
соединений в одну секунду — это отдельный разговор про совсем другой бюджет.

---

## Где ломается нынешняя машина (961 МБ, 1 ядро, SQLite)

Точки отказа не предполагаемые — все три измерены авариями (журнал в CLAUDE.md):

| Что | Предел | Замер |
|---|---|---|
| Память воркера | ~200 МБ на процесс | OOM-петля 01.08, 10 261 рестарт, load average 15 |
| Одно ядро под ffmpeg | 1 перекодирование = ядро целиком | серия скачиваний дважды уронила sshd 14.08 |
| SQLite под нагрузкой | writer блокирует readers | «database is locked», лечили WAL + busy_timeout |
| Своп при нехватке RAM | поиск до 19 сек | 03.08, очередь Redis выдавила процессы в своп |

Практический потолок сейчас: **десятки активных пользователей**. Сегодня их 37,
активных за неделю — 3. То есть даже до сотни одновременных далеко.

Синтетический нагрузочный тест этого бокса я делать не стал намеренно: он
обслуживает живых людей и владельца, а его точки отказа уже известны из аварий —
флуд лишь повторил бы их, положив прод. Вместо этого добавлен лимитер частоты на
API (первая линия обороны, уже задеплоен).

---

## Что уже готово к масштабу

- **Stateless-архитектура.** Бот и API не держат состояние в процессе (кроме
  счётчиков антифлуда) — FSM в Redis, данные в БД. Значит масштабируются
  горизонтально: несколько экземпляров за балансировщиком.
- **Тяжёлое вынесено в Celery.** Скачивание и перекодирование не в процессе бота
  — воркеры масштабируются отдельно от бота.
- **Живой поиск без каталога.** Не нужно хранить и индексировать миллионы треков:
  источник спрашивается вживую, популярное греется в архивный канал.
- **Аудио хранит Telegram.** Наш диск не растёт от числа треков — только БД,
  ~1.7 КБ на трек (замер: 7448 треков = 13 МБ). Миллион треков ≈ 1.7 ГБ.

## Архитектура на 1 млн зарегистрированных

Порядок — по мере роста, не всё сразу.

### Шаг 1. Один нормальный сервер (первые ~10 тыс. пользователей)
- 4 ядра / 8 ГБ / SSD. Снимает разом все четыре точки отказа выше.
- **PostgreSQL** вместо SQLite (миграции Alembic уже есть; см. новая-машина.md §1).
  Заодно чинит кириллический `ILIKE` — на SQLite поиск по базе регистрозависим.
- Celery: 3–4 воркера скачивания вместо одного на threads-пуле.
- Redis отдельно, с `maxmemory` и политикой вытеснения.

### Шаг 2. Разделение ролей (~100 тыс.)
- Бот, API, воркеры — на разных машинах.
- PostgreSQL на своей машине, read-реплика для API (выдача каталога — чтение).
- Redis Sentinel/кластер для отказоустойчивости FSM и брокера.
- CDN перед статикой Mini App (сейчас её отдаёт nginx напрямую).

### Шаг 3. Горизонталь (~1 млн)
- Несколько экземпляров бота через Telegram **webhook** вместо polling
  (polling — один потребитель; webhook балансируется на несколько инстансов).
  ⚠️ Это переписывание точки входа: сейчас `app/main.py` на polling.
- API за балансировщиком, N реплик (уже stateless — кроме лимитера частоты:
  его память придётся вынести в Redis, иначе каждый инстанс считает свой лимит).
- PostgreSQL с пулером (PgBouncer) и шардированием при необходимости.
- Пул воркеров скачивания под очередь, автоскейл по длине очереди.
- Прогрев каталога переходит из «30 треков за ночь» в постоянный: чем больше
  заминчено заранее, тем меньше живых скачиваний в пик.

### Что переписать в коде (не решается железом)
1. **Лимитер частоты API** — сейчас в памяти процесса. При нескольких инстансах
   считать в Redis (иначе N инстансов = N×лимит).
2. **Антифлуд бота** — та же история, память процесса → Redis, при нескольких
   инстансах бота.
3. **Polling → webhook** — для нескольких экземпляров бота.
4. **Счётчики file_id-health и кэш вердиктов** — тоже память процесса.

Всё остальное (сервисы, задачи, схема БД) масштабируется без переписывания.

## Честный вывод

«Включить 1 млн» одной командой нельзя — это не настройка, а перестройка под
рост. Но фундамент к ней готов: stateless-сервисы, тяжёлое в очереди, поиск без
каталога, аудио у Telegram. Узкие места известны поимённо, и первый же нормальный
сервер (шаг 1) поднимает потолок с десятков до тысяч. Дальше — по мере того, как
пользователи реально появятся (см. growth.md); строить шаг 3 на 37 пользователях
преждевременно.
