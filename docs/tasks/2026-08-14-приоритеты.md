## Замеры, от которых нужно отталкиваться

Всё измерено на проде 13–14.08, а не предположено.

| Что | Сколько |
|---|---|
| Поиск в SoundCloud | 0.18–0.28 сек (среднее 0.22) |
| Уже заминченный трек | доли секунды, уходит по `file_id` без сети |
| Новый трек: скачать + залить в Telegram | около 8 сек |
| Скачивание mp3 128 | 6.59 сек |
| Скачивание AAC 160 | 7.25 сек |
| Оригинал автора доступен | 6 треков из 601 = **1%** |

**Главное следствие.** «Быстро» упирается не в наш код, а в источник: 8 секунд
это скачивание у SoundCloud плюс заливка в Telegram. Мгновенно уходит только то,
что уже заминчено. Значит единственный рычаг для «за секунду» — **прогрев
каталога**, а не оптимизация.

## 🔴 YouTube починен: прокси + tv_embedded (14.08)

⚠️ **Здесь была моя ошибка, и она стоила бы дорого.** Сначала я записал, что VPN
YouTube не лечит. Замер обманул: `ignoreerrors=True` глушит ошибку yt-dlp и
отдаёт пустой результат, а снаружи «пусто» неотличимо от «заблокировано».
Повторный замер с `ignoreerrors=False` показал обратное.

**Что выяснилось на самом деле:**

| Проверка | Результат |
|---|---|
| yt-dlp | уже последней версии (2026.07.04) — обновлять нечего |
| Все 10 player-клиентов напрямую | отказ «Sign in to confirm you're not a bot» |
| Прокси + клиент по умолчанию | метаданные есть, медиа-URL отдают 403 |
| Только `tv_embedded` без прокси | тот же «Sign in» |
| **Прокси + `tv_embedded`** | **работает** |

То есть блокировка по IP сервера, и снимается она только связкой: ни прокси сам
по себе, ни клиент сам по себе не помогают.

**Проверка на живых треках после деплоя:** 3 из 4 скачались (Eminem — Lose
Yourself, Daft Punk — One More Time, Kendrick Lamar — HUMBLE), «Blinding Lights»
в этот заход не дался, хотя в предыдущем дался. Было 0 из 4. Отказы плавают от
попытки к попытке — похоже на конкретный выходной узел, а не на нас.

**Цена:** 12–19 сек против 7 у SoundCloud. Разница не в сети, а в ffmpeg:
`tv_embedded` отдаёт opus в webm, который Telegram не играет, и его приходится
перекодировать в mp3 на единственном ядре. YouTube у нас фолбэк, так что эти
секунды платятся только там, где SoundCloud не справился.

**Настройки** (на сервере в `.env`, в репозитории только значения по умолчанию):
`YOUTUBE_PROXY=socks5://127.0.0.1:10808`, `YOUTUBE_PLAYER_CLIENT=tv_embedded`.
`PROXY_LIST` остаётся пустым: SoundCloud через тот же VPN идёт с той же
скоростью (6.22 против 6.83 сек), лишний узел на главном источнике не нужен.

### ✅ Закрыто 16.08 — и вышло не так, как здесь написано

Замер по каждому выходу отдельно (`python -m app.cli.youtube_exits`) показал, что
**живой узел один, а не пять**: 10808 и 10813 ведут в один и тот же шведский
выход (5/5 и 4/5), а 10811, 10812, 10814 и 10815 отвечают «Sign in» всегда.
В `.env` при этом стоял **10815 — из мёртвых**, то есть YouTube не работал вовсе.
Замер 14.08 с его «3 из 4» шёл через 10808 и потому получался.

Перебирать по кругу было нечего — нужны были новые узлы. **Владелец прислал их в
тот же день**, и вопрос закрылся: из шести новых конфигов живы четыре (🇺🇸 США и
🇪🇺 Hysteria по 5 из 5, две 🇱🇹 Литвы по 4 из 5; оба 🇳🇱 Нидерландов мертвы).

Итого **пять живых выходов в разных странах** вместо одного — ротация из этого
файла наконец имеет смысл. Сквозная проверка: скачивание 3.54 МБ за 14 сек.
Ночная `--check` пишет админу, если выходы начнут выбывать.

⚠️ Узлы заводятся в Xray отдельными socks-входами (10821–10826), правило
маршрутизации вставляется В НАЧАЛО списка: ниже лежат общие правила («`.ru`
напрямую»), и они сработали бы первыми. У grpc-узлов `flow` обязан быть пустым —
`xtls-rprx-vision` работает только поверх tcp.

### Исходный план (оставлен для истории): ротация выходов

Сейчас Xray поднят с ОДНИМ socks-входом (10808) и пятью VLESS-выходами, то есть
реально используется один выход. Отказы плавают именно по выходам — значит
ротация должна поднять 3 из 4 ближе к четырём из четырёх.

Как: пять socks-входов (10808–10812), каждый маршрутизируется в свой выход
правилом `inboundTag → outboundTag`, один процесс Xray и один юнит. В коде —
список прокси вместо одной строки и перебор по кругу, ровно как уже сделано для
`PROXY_LIST` в `services/proxies.py`.

### Про авторизацию

Куки Google-аккаунта (`YOUTUBE_COOKIES_PATH`) поддержаны в коде, но **сейчас не
нужны**: связка прокси + `tv_embedded` закрывает вопрос без единого аккаунта, а
значит и без риска, что аккаунт забанят за автоматические скачивания. Заводить
куки имеет смысл, только если YouTube закроет и этот путь. Тогда — отдельный
аккаунт, не основной, и файл с правами 600 на сервере, не в переписке.

⚠️ Куки, которые владелец дважды присылал в чат, скомпрометированы: те сессии
надо отозвать.

⚠️ Конфиги VPN тоже пришли в чат — UUID и приватные ключи открытым текстом.
Подписка личная; если она платная и общая с кем-то, стоит перевыпустить.

## 1. КРАСИВО

Что уже сделано и работает: обложка вшивается в файл и отдаётся отдельной
миниатюрой 200×200 (без неё плеер Telegram показывал трек без картинки),
ID3-теги перетегируются, имя файла «Исполнитель — Название.ext», карточка с
кнопками под треком, исполнитель берётся из `publisher_metadata` → разбора
заголовка → и только потом из имени аккаунта.

Что осталось:

- **Ранжирование инлайн-выдачи.** Инлайн ищет по локальной базе, и по запросу
  «kizaru» первым идёт «044ROSE — STOP XANAX ДЭМО ДЛЯ КИЗАРУ». Живое
  ранжирование туда не подключено — это самая заметная некрасивость из
  оставшихся.
- **Старые треки без миниатюры.** Превью появляется только у заново заминченных;
  у 7.4 тысяч старых `file_id` уже без него. Лечится только повторным минтом.
- **Мусор в названиях каталога**: «(Official Audio)», «prod. by», «[FREE]».
  Чистится при импорте, но у старых записей осталось.

## 2. БЫСТРО

Сделано: поиск ускорен в 8–20 раз (одно keep-alive соединение вместо нового TLS
на каждый вызов), отпечаток убран из живого пути, обложки грузятся параллельно,
SoundCloud отдаёт готовый mp3 без перекодирования.

Что осталось — **только прогрев каталога**. `app.cli.warmup` заранее минтит
популярные запросы, после чего они уходят мгновенно. Владелец сильный прогрев
делать не хотел; разумный компромисс — `warmup --popular 30` в ежедневный
таймер: 30 треков в сутки бесплатно и незаметно для сервера.

⚠️ Потолок каталога считать по базе, а не по аудио: ~1.7 КБ на трек после
чистки, то есть 100 тысяч ≈ 170 МБ. Аудио хранит Telegram.

## 3. ОРИГИНАЛ

Сделано: режим «Лучшее качество» (⚙️ Настройки), лестница форматов оригинал
автора → 160 kbps → 128 kbps, отдельная копия для подписчиков в `hq_file_id`.

Что мешает большему — и это **не наш код**:

- оригинал автора доступен у 1% треков, остальные его закрыли;
- даже у доступных yt-dlp с анонимным `client_id` ссылку на исходник не получает
  — эндпоинт скачивания требует авторизации;
- DRM-треки (мейджоры) не скачиваются в принципе, и обходить защиту мы не будем.

**Единственный честный путь к настоящему FLAC** — легальный доступ:
аккаунт SoundCloud Go+ с OAuth-токеном либо датасет от правообладателя, который
импортируется через `app.cli.import_catalog`. Второе закрывает разом и «любой
трек», и «за секунду».

## Порядок работ

1. **Прогрев в таймер** (`warmup --popular 30`) — единственный рычаг «быстро»,
   дешёвый и обратимый.
2. **Ранжирование инлайн-выдачи** — самая заметная некрасивость.
3. **Ротация выходов VPN** — поднять 3 из 4 на YouTube ближе к четырём из четырёх.
4. **Переезд на два ядра** — блокер импорта плейлистов целиком.
5. Партнёрская программа Telegram — действие владельца в @BotFather.
