## Мой поиск отвечал 4 секунды. Я оптимизировал алгоритм, а платил за TLS-рукопожатие

Я делаю музыкального бота для Telegram: человек пишет название трека, бот ищет
его в открытых источниках и присылает файлом. Главная претензия пользователей
была всегда одна — «медленно». Поиск отвечал от 1.9 до 4.7 секунды, а в плохие
минуты доходило до девятнадцати.

Полгода я был уверен, что проблема в алгоритме: слишком много кандидатов,
слишком тяжёлое ранжирование, надо кэшировать агрессивнее. Оказалось, что
алгоритм тут почти ни при чём. Расскажу, как искал и что нашёл, — история
банальная ровно настолько, чтобы в неё вляпаться второй раз.

### Как было устроено

Поиск шёл через `yt-dlp`. Это отличная библиотека, и для скачивания аудио ей нет
замены: она знает про форматы, про плейлисты, про то, как отдаёт данные каждый
конкретный хостинг. Логично было использовать её и для поиска — у неё есть
псевдо-URL вида `scsearch15:запрос`, который возвращает список результатов.

Работало это так:

1. запрос как есть → `scsearch`;
2. тот же запрос в транслите (у меня много кириллицы, а названия на латинице) →
   ещё один `scsearch`;
3. если результатов мало — добавляется YouTube → `ytsearch`.

То есть один пользовательский запрос превращался в два-три вызова `yt-dlp`.

### Первая попытка: оптимизировать не то

Я сделал то, что делают все. Прикрутил кэш выдачи в Redis. Урезал число
кандидатов. Убрал часть проверок из ранжирования. Распараллелил источники через
`asyncio.gather`, чтобы SoundCloud и YouTube опрашивались одновременно.

Параллелизм дал реальный выигрыш — время стало равно медленному из двух
источников, а не их сумме. Всё остальное не дало почти ничего. Кэш помогал
только на повторных запросах, а музыку люди ищут разную.

Тогда я перестал угадывать и сделал то, с чего надо было начинать.

### Замер

Я разнёс по времени три вещи: сетевой вызов, разбор ответа и ранжирование.

Результат оказался неприличным. Ранжирование — единицы миллисекунд. Разбор
ответа — тоже. Практически всё время уходило в сеть. Причём внутри «сети»
картина была такая:

- новое соединение до хоста — **8.5 секунды** в худшем случае;
- переиспользованное соединение к тому же хосту — **0.66–0.93 секунды**.

Разница в десять раз. И вот тут стало понятно, где я жил всё это время.

`yt-dlp` — это инструмент, спроектированный под сценарий «запустился, скачал,
вышел». Он на каждый вызов поднимает свой экстрактор и **новое TLS-соединение**.
Внутри долгоживущего процесса воркера это означает, что каждый поиск заново
платит за DNS, TCP-хендшейк и TLS-хендшейк. Два-три раза за один запрос
пользователя.

Я оптимизировал алгоритм, который занимал миллисекунды, и не трогал рукопожатие,
которое занимало секунды.

### Что сделал

SoundCloud, который у меня основной источник, имеет публичный JSON-API —
`api-v2.soundcloud.com`, тот самый, которым пользуется их собственный веб-плеер.
Для поиска мне не нужен `yt-dlp` вообще: нужен один GET и разбор JSON.

Ключевое — не «пойти напрямую», а **держать одно живое соединение на процесс**:

```python
_API_HOST = "api-v2.soundcloud.com"
_HEADERS = {"User-Agent": _UA, "Accept": "application/json", "Connection": "keep-alive"}

_lock = threading.Lock()
_connection: http.client.HTTPSConnection | None = None


def _request(path: str) -> bytes | None:
    """GET по живому соединению. Разорвалось — пересоздаём и повторяем один раз."""
    global _connection
    for attempt in (1, 2):
        try:
            if _connection is None:
                _connection = http.client.HTTPSConnection(_API_HOST, timeout=_TIMEOUT)
            _connection.request("GET", path, headers=_HEADERS)
            response = _connection.getresponse()
            body = response.read()
            if response.status == 401:
                return None          # ключ протух, обновит вызывающий
            if response.status != 200:
                return None
            return body
        except Exception:
            # соединение умерло — закрываем и идём на вторую попытку со свежим
            if _connection is not None:
                try:
                    _connection.close()
                except Exception:
                    pass
            _connection = None
            if attempt == 2:
                return None
    return None
```

Здесь важны три вещи, каждая из которых стоила мне отдельной ошибки.

**Соединение обязано уметь умирать.** Keep-alive со стороны сервера живёт не
вечно: хост закроет его по таймауту, а вы об этом узнаете только в момент
следующего запроса — исключением. Поэтому цикл на две попытки: первая может
упасть на протухшем сокете, вторая идёт по свежему. Без этого вы меняете
«медленно всегда» на «быстро, но иногда 500».

**Общее состояние — под замком.** Провайдер вызывается из `asyncio.to_thread`,
то есть из нескольких потоков. Одно соединение на процесс означает, что два
потока могут одновременно писать запрос и читать ответ в один сокет — и получить
чужой ответ на свой запрос. `threading.Lock` вокруг обращения обязателен. Да,
это сериализует запросы к SoundCloud, но при 0.2 секунды на запрос это дешевле,
чем пул соединений и его отладка.

**Публичный ключ надо кэшировать не там, где кажется.** API требует `client_id` —
публичный ключ веб-плеера. Добывается он честным способом: скачать JS-бандлы
SoundCloud и вынуть регуляркой. Проблема в том, что бандлов несколько и это
**почти 20 секунд**. Если хранить ключ только в памяти процесса, то первый
человек после каждого рестарта воркера платит эти 20 секунд за всех. Ключ уехал
в Redis с TTL в сутки, а при ответе 401 обновляется принудительно.

### Что осталось от yt-dlp

Всё скачивание. Заменять его там я даже не пробовал: там он незаменим.

Плюс он остался **запасным путём поиска**. Если SoundCloud сменит формат ответа
или забанит ключ, поиск не умрёт — он станет медленным, как раньше. Это
осознанный размен: держать деградацию вместо отказа. Пустой ответ от API — не
повод возвращать пользователю «ничего не найдено», а повод сходить длинным
путём.

Кстати, про пустой ответ. У `yt-dlp` есть опция `ignoreerrors=True`, и она
сыграла со мной злую шутку в соседнем месте: при сетевой ошибке библиотека
гасит исключение сама и возвращает словарь с **пустым `entries`**. Снаружи это
неотличимо от честного «по вашему запросу ничего нет». У меня из-за этого
несколько месяцев молча не работал целый источник, а выглядело это как «поиск
слабый, андеграунд не находит».

### Результат

Замер на боевом сервере:

- первый запрос после старта — **0.79 секунды** (поднимаем соединение);
- дальше — **0.18–0.28 секунды**, в среднем **0.22**.

Было 1.9–4.7. Ускорение в 8–20 раз, и ни строчки в ранжировании я для этого не
поменял.

### Чего это не решает

Честно скажу, где потолок. Быстрый поиск — это быстрый **список вариантов**.
Если трека ещё нет в базе, после выбора его надо скачать, а это 7–14 секунд, и
здесь предел ставит источник, а не мой код. Доли секунды получает только тот,
кто просит уже загруженный трек: он уходит по идентификатору файла, вообще без
сети.

То есть я ускорил ту часть, которую видел пользователь первой, и теперь упёрся в
следующую. Это нормальный порядок вещей.

### Выводы, которые я бы хотел прочитать полгода назад

1. **Измеряйте раньше, чем оптимизируете.** Звучит как банальность из учебника,
   ровно до того момента, когда вы полгода полируете код, занимающий 1% времени.
2. **Библиотека, спроектированная под CLI, внутри демона ведёт себя иначе.**
   «Запустился и вышел» — это отсутствие переиспользования соединений, и в
   долгоживущем процессе за это платят каждым запросом.
3. **Рукопожатие дороже запроса.** Если ваш сервис ходит к одному и тому же
   хосту много раз, keep-alive-соединение — обычно самое дешёвое ускорение из
   существующих.
4. **Глушение ошибок опаснее ошибок.** Флаг, превращающий сбой в пустой
   результат, скрывает поломку в месте, где вы никогда не будете её искать.
