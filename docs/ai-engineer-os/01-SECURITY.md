## §1. Аутентификация

Разделять два разных вопроса:

```
Аутентификация: кто ты?
Авторизация:    что тебе можно?
```

Проверить:

- [ ] Личность устанавливает **сервер**, из проверенного источника. Не из тела запроса.
- [ ] Токен подписан, срок жизни ограничен, срок проверяется **после** проверки подписи.
- [ ] Подпись подтверждает происхождение, но **не время**. Свежесть — отдельная проверка.
- [ ] Секрет подписи не пустой, не дефолтный, не совпадает с другим секретом без причины.
- [ ] Токен не передаётся в URL (попадает в логи, историю, `Referer`).
- [ ] Токен не пишется в логи.
- [ ] Истёкший токен даёт понятный ответ, а клиент умеет перевыпустить без бесконечного цикла 401.
- [ ] Выход/отзыв: есть способ прекратить доступ, если токен утёк.

**Ловушка.** Проверка срока действия, поставленная **перед** проверкой подписи,
бесполезна: злоумышленник подделает поле времени. Порядок обязателен:
сначала подпись, потом свежесть. На это нужен отдельный тест.

## §2. Авторизация и владение ресурсом (A01 — самая частая категория)

Главный вопрос на каждом эндпоинте, работающем с ресурсом:

> Проверяется «существует ли ресурс» или «принадлежит ли он текущему пользователю»?

Первое — дыра. Второе — правильно.

```
ПЛОХО:  SELECT * FROM orders WHERE id = :id
ХОРОШО: SELECT * FROM orders WHERE id = :id AND user_id = :current_user_id
```

Проверить:

- [ ] Каждый эндпоинт, принимающий id ресурса, сверяет владение или явное право.
- [ ] Чужой ресурс отдаёт `404`, а не `403` — `403` подтверждает существование.
- [ ] Права проверяются на сервере, а не показом/скрытием кнопки.
- [ ] Роли хранятся на сервере; клиент не может прислать `role`.
- [ ] Служебные и «внутренние» эндпоинты закрыты так же, как основные.
- [ ] Массовые операции (список, экспорт, поиск) фильтруются по владельцу, а не отдают всё.
- [ ] Перебор id не даёт информации (последовательные id — само по себе не дыра, но упрощает перебор).
- [ ] **SSRF**: если сервер ходит по URL, пришедшему от пользователя, — проверять
      схему, хост, отсутствие приватных диапазонов и редиректов внутрь сети.

### Матрица прав

Для проекта с ролями строится таблица и **проверяется тестами**:

| Действие | Гость | Юзер | Премиум | Админ |
|---|---|---|---|---|
| … | | | | |

Тест обязателен на клетку «нельзя»: пользователь A не получает ресурс B.

## §3. Валидация входных данных

Правило: **валидировать на сервере всё, что пришло снаружи**, даже если фронт уже проверил.

Для каждого поля определить: тип, диапазон, длину, формат, допустимые значения.

Обязательные потолки (их забывают чаще всего):

- [ ] Размер тела запроса
- [ ] Длина каждой строки
- [ ] Число элементов в массиве
- [ ] `page_size` / `limit` — верхняя граница константой
- [ ] Глубина вложенности JSON
- [ ] Размер и число файлов

Проверить поведение на: `null`, `{}`, `[]`, `""`, `0`, `-1`, `999999999999`,
`NaN`, строка вместо числа, число вместо строки, кривой UTF-8, эмодзи,
управляющие символы, очень длинная строка, дубли ключей в JSON.

Ожидаемый результат: понятная ошибка `400`, а не `500` и не падение процесса.

## §4. Инъекции (A05)

**SQL.** Только параметризованные запросы или ORM. Никакой склейки строк.
Опасные места, которые ORM не спасает: динамическая сортировка (`ORDER BY` из
запроса), динамическое имя колонки, `LIKE` с неэкранированными `%`/`_`, сырые
фрагменты SQL.

- [ ] Нет конкатенации пользовательского ввода в SQL
- [ ] Сортировка — из белого списка колонок
- [ ] `LIKE`-шаблон экранируется

**Команды ОС.** Не собирать команду строкой. Аргументы — списком, без shell.
Пути, приходящие снаружи, — нормализовать и проверить, что остались внутри
разрешённого каталога (path traversal).

**Шаблоны и разметка.** Если текст уходит в HTML/Markdown Telegram — экранировать
под конкретный формат. Названия треков, имена артистов, ники — **чужой текст**.

## §5. Гонки и параллельные запросы

Вопрос к каждой операции, которая что-то выдаёт, начисляет, списывает или создаёт:

> Что произойдёт, если два одинаковых запроса придут одновременно?

Типовые последствия: двойное начисление, две записи вместо одной, потерянное
обновление, обход лимита «один раз в день».

Инструменты (выбирать по ситуации, а не все сразу):

- уникальный индекс в БД — самая дешёвая и надёжная защита;
- транзакция с блокировкой строки (`SELECT ... FOR UPDATE`);
- атомарный `UPDATE ... WHERE` с проверкой прежнего состояния (optimistic);
- распределённая блокировка в Redis с TTL — для межпроцессных случаев;
- дедуп по ключу операции на входе.

- [ ] Проверено на двойном клике
- [ ] Проверено на двух параллельных HTTP-запросах
- [ ] Проверено на повторной доставке задачи в очередь
- [ ] Уникальность гарантируется БД, а не проверкой «существует ли» перед вставкой

**Ловушка.** `if not exists: create()` — не защита. Между проверкой и вставкой
проходит время, и туда влезает второй процесс. Нужен уникальный индекс.

## §6. Идемпотентность

Повтор операции не должен выполнять критическое действие второй раз.

Где обязательна: платежи, вебхуки, начисления, отправка сообщений, задачи в
очереди (доставка «как минимум один раз» — норма для брокеров), кнопки в UI.

Схема:

```
Запрос с ключом операции
  ↓
Ключ уже обработан? → вернуть прежний результат, ничего не делать
  ↓
Выполнить в транзакции: действие + запись ключа
```

- [ ] У каждой денежной операции есть ключ идемпотентности
- [ ] Повторный вебхук проверен вручную и не создаёт вторую запись
- [ ] Повторная задача Celery не плодит дубликаты
- [ ] Кнопка защищена от двойного нажатия и на клиенте, и на сервере

---

## §7. Секреты и криптография (A04)

- [ ] Секреты только в переменных окружения / секрет-хранилище
- [ ] Секретов нет: во фронтенде, в бандле JS, в git-истории, в образе, в логах, в ответах API, в сообщениях об ошибках
- [ ] Проверен не только рабочий каталог, но и **история git** (утёкший секрет надо отзывать, а не удалять коммитом)
- [ ] Сравнение секретов — постоянное по времени (`compare_digest`), не `==`
- [ ] Подписи с ограниченным сроком у всего, что уходит наружу ссылкой
- [ ] Криптография — из стандартной библиотеки, не самописная
- [ ] Смена секрета возможна без переписывания кода

**Утечка секрета в переписку или скриншот = секрет скомпрометирован.**
Удаление сообщения не помогает. Единственная реакция — перевыпуск.

---

## §8. Загрузка и выдача файлов

- [ ] Ограничен размер и количество
- [ ] Тип проверяется по содержимому, а не только по расширению и заголовку
- [ ] Имя файла не используется как путь; ключ хранения собирается из id
- [ ] Path traversal невозможен (`../`, абсолютный путь, символьные ссылки)
- [ ] Загруженное не выполняется сервером
- [ ] SVG и HTML от пользователя не отдаются с исходным `Content-Type` без санитизации
- [ ] `X-Content-Type-Options: nosniff` на выдаче
- [ ] Доступ к файлу проверяется так же, как к любому ресурсу (§2)
- [ ] Есть защита диска: гейт по свободному месту, ротация, лимит на пользователя

---

## §9. Цепочка поставок (A03 — новая категория 2025)

- [ ] Версии зафиксированы (lock-файл), а не «последняя»
- [ ] Известные уязвимости проверяются регулярно, а не однократно
- [ ] Нет заброшенных пакетов в критичных местах
- [ ] Базовый образ контейнера минимальный и обновляется
- [ ] Шаги CI (сторонние actions) закреплены по версии
- [ ] Новая зависимость добавляется осознанно: что она делает, кто её ведёт, можно ли без неё

**Отдельно для ИИ-кода:** не добавлять зависимость ради одной функции, которую
можно написать в десять строк. Каждая библиотека — новая поверхность атаки.

## §10. Безопасность бизнес-логики

Самый недооценённый класс. Здесь нет SQL-инъекций — есть неверные правила.

Вопросы:

- Можно ли применить скидку дважды?
- Можно ли получить награду повторно, отменив и повторив действие?
- Можно ли накрутить счётчик, от которого зависит выгода (рефералы, рейтинг, прослушивания)?
- Можно ли перевести объект в состояние, из которого он не должен возвращаться?
- Можно ли обойти лимит через другой путь в интерфейсе?
- Можно ли сделать операцию за другого пользователя, оставаясь в своих правах?

Для сущностей со статусами — выписать конечный автомат и запретить невозможные
переходы **в коде**, а не «мы так не делаем»:

```
pending → processing → completed
completed ↛ pending          (запрещено)
```

- [ ] Автомат состояний описан и проверяется тестами
- [ ] Накрутка счётчиков, влияющих на выгоду, ограничена (дедуп по времени, критерий «живого» действия)
- [ ] Бизнес-лимит отделён от rate limit (это разные механизмы, см. §12)

---

## §11. Обработка исключительных ситуаций (A10 — новая категория 2025)

Разделять три разных исхода — их постоянно склеивают в один:

```
Успех, есть данные       → результат
Успех, данных нет        → пусто (это тоже успех)
Отказ                    → ОШИБКА, и она обязана быть отличима от пустоты
```

- [ ] Отказ внешнего источника не выглядит как «ничего не найдено»
- [ ] Отказ не кэшируется как отрицательный ответ
- [ ] Нет «глухих» `except`, глотающих всё подряд
- [ ] Fail-closed или fail-open выбран **осознанно** и записан (для доступа — closed, для необязательной функции — open)
- [ ] Наружу уходит понятное сообщение и код, внутрь — трассировка в лог
- [ ] Пользователь не видит SQL, путей файлов, имён таблиц, версий библиотек
- [ ] Частично выполненная операция оставляет консистентное состояние (транзакция или компенсация)

**Ловушка проекта.** Библиотека с флагом «игнорировать ошибки» превращает
сетевой отказ в пустой результат. Снаружи это неотличимо от «не найдено», и код
принимает неверное решение. Такие флаги выключать.

---

## §12. Лимиты

Два разных механизма, которые нельзя путать:

```
Rate limit:     100 запросов в минуту        (защита инфраструктуры)
Бизнес-лимит:   1 бонус в сутки              (защита экономики)
```

- [ ] Лимит на вход по пользователю и по IP
- [ ] Лимиты на дорогие операции отдельно от дешёвых
- [ ] Счётчики лимитов не растут вечно — есть уборка (иначе это утечка памяти)
- [ ] Заблокированные попытки тоже считаются, иначе машинный шквал неотличим от человека
- [ ] Предупреждение о флуде отправляется **один раз на серию**, а не на каждый запрос (иначе сервис флудит сам)
- [ ] Бизнес-лимит проверяется в транзакции (иначе обходится гонкой, §5)

---

## §13. Чек-лист аудита безопасности

```
[ ] Матрица прав составлена, «нельзя» покрыто тестами
[ ] Каждый эндпоинт с id ресурса проверяет владение
[ ] Личность и роль вычисляются сервером
[ ] Свежесть подписи проверяется после подписи
[ ] Валидация на сервере, потолки на объём заданы
[ ] Параметризованные запросы, белый список сортировки
[ ] Гонки проверены на ключевых операциях
[ ] Денежные и внешние операции идемпотентны
[ ] Секретов нет во фронте, логах, образе, истории git
[ ] Файлы: тип, размер, путь, доступ
[ ] Зависимости зафиксированы и проверены
[ ] Бизнес-логика: автоматы состояний, накрутка, лимиты
[ ] Отказ отличим от пустоты и не кэшируется
[ ] Наружу не уходит внутренняя информация
```
