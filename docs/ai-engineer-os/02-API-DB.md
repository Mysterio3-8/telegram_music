# 02 — API И БАЗА ДАННЫХ

---

## §1. API — это публичный контракт

Эндпоинт вызывают не только твой фронтенд. Его вызывают напрямую, с любыми
параметрами, в любом порядке, тысячу раз в секунду.

### Паспорт эндпоинта

Для каждого нового эндпоинта заполняется:

```
Путь и метод:
Назначение:
Кто может вызвать:        (гость / юзер / премиум / админ / внутренний)
Как определяется личность:
Проверка владения:        (какой ресурс, по какому полю)
Вход:                     (схема, обязательные, потолки)
Выход:                    (схема; каких полей там быть НЕ должно)
Ошибки:                   (коды и что означают)
Лимит:                    (rate + бизнес-лимит)
Идемпотентность:          (нужна? по какому ключу?)
Побочные эффекты:         (записи в БД, отправки, задачи в очередь, деньги)
Стоимость:                (сколько запросов к БД/сети — можно ли этим уронить сервис)
```

Если в графе «Кто может вызвать» стоит что-то кроме «гость», в коде должна быть
явная проверка. «Оно под общим мидлваром» — проверить и подтвердить, а не поверить.

### Обязательные проверки

- [ ] У каждого непубличного эндпоинта есть зависимость авторизации
- [ ] Список публичных эндпоинтов выписан явно и обоснован
- [ ] Ответ не содержит лишнего: чужих id, внутренних флагов, путей, хэшей, служебных полей
- [ ] Пагинация есть везде, где список может вырасти; `page_size` ограничен сверху
- [ ] Ошибки единообразны: код + краткое сообщение, без внутренностей
- [ ] Тяжёлые операции не выполняются внутри запроса — уходят в очередь
- [ ] Есть версионирование или осознанное решение его не иметь

## §2. Стоимость запроса

Вопрос: **сколько работы делает один вызов?**

Классическая ошибка ИИ-кода: листать данные циклом по страницам внутри одного
эндпоинта. Подборка на 500 элементов при странице 5 — сто последовательных
запросов к БД за один вызов. Внешне работает, под нагрузкой убивает сервис.

- [ ] Нет циклов «страница за страницей» внутри одного вызова — один запрос с лимитом
- [ ] Нет N+1: список объектов не тянет связанные данные по одному
- [ ] Нет полных сканов таблицы на горячем пути
- [ ] Объём ответа ограничен
- [ ] Дорогие вычисления кэшируются или считаются заранее

Проверять **планом запроса**, а не на глаз. `EXPLAIN` показывает, идёт запрос по
индексу или сканирует таблицу целиком.

## §3. Схема БД

- [ ] Внешние ключи заданы
- [ ] Уникальные ограничения там, где дубликат недопустим (это же защита от гонок)
- [ ] `NOT NULL` там, где значение обязательно
- [ ] Различаются `NULL` («не знаем») и `0`/`false` («знаем: ноль»).
      Склеивание этих двух смыслов уже давало неверное ранжирование в этом проекте
- [ ] Денежные суммы — целые в минимальных единицах, не float
- [ ] Время — в UTC, с явной таймзоной
- [ ] Схема меняется **только миграциями**, не `create_all`

---

## §4. Индексы

- [ ] Индекс есть на каждое поле, по которому идёт частая фильтрация или сортировка
- [ ] Составные индексы — в порядке, соответствующем запросам
- [ ] Частичные индексы там, где почти всё `NULL` (весит килобайты вместо мегабайт)
- [ ] Проверено планом, что индекс реально используется
- [ ] Проверен размер индексов: индекс, сравнимый с таблицей, — повод пересмотреть,
      что именно индексируется

Полный скан большой таблицы на маленькой машине читает её с диска заново каждый
раз — страничный кэш вытесняется. Симптом: «экран открывается 5 секунд».

---

## §5. Транзакции и целостность

- [ ] Операция, меняющая несколько таблиц, идёт в одной транзакции
- [ ] Понятно, что произойдёт при обрыве посередине
- [ ] Уровень изоляции достаточен для операций «прочитал → решил → записал»
- [ ] Блокировки короткие; нет удержания транзакции на время сетевого вызова
- [ ] Внешний вызов (платёжка, Telegram) **не внутри** транзакции БД
- [ ] Нет осиротевших связей после удалений
- [ ] Мягкое удаление vs жёсткое — выбрано осознанно

**Правило удаления данных, собранных пользователями.** Прежде чем удалять по
критерию — посчитать, сколько из удаляемого лежит в чьих-то библиотеках и
плейлистах. Восстановить сам объект можно, а дыру в чужом плейлисте — нельзя.
Защита включена по умолчанию; снятие — осознанная потеря.

**Слияние вместо удаления.** При разборе дублей данные пользователей (библиотеки,
плейлисты, статистика) переносятся на остающуюся запись, и только осиротевшая
удаляется. Оставлять — сперва рабочую копию, затем самую востребованную, затем
самую старую.

---

## §6. Миграции

- [ ] Каждое изменение схемы — миграция в репозитории
- [ ] Миграция проверена на копии реальных данных, а не на пустой БД
- [ ] Есть путь назад (`downgrade`) или явное решение, что его нет
- [ ] Миграция не блокирует таблицу надолго на проде
- [ ] Обратная совместимость: старый код не падает на новой схеме в момент деплоя
- [ ] Бэкфилл больших таблиц идёт пачками, а не одним `UPDATE`
- [ ] Перед адаптацией существующей БД без версии — `stamp` на соответствующую ревизию, затем `upgrade`

## §7. Специфика SQLite (пока прод на нём)

- [ ] Включён WAL, задан `busy_timeout` — иначе писатель блокирует читателей
- [ ] **Все** процессы (бот, API, воркеры) создают соединение через общую фабрику
      с одинаковыми PRAGMA. Отдельный engine без PRAGMA — источник «database is locked»
- [ ] `lower()` и `ilike` **не понижают кириллицу**. Любое сравнение с
      пользовательским текстом — по нормализованной в Python колонке.
      Этот баг здесь ломал: поиск, привязку артистов, дедуп при импорте
- [ ] Оценка роста базы сделана в килобайтах на запись, а не «по объёму медиа»
- [ ] Понятен порог, за которым нужен PostgreSQL, и он записан

---

## §8. Очереди и фоновые задачи

- [ ] Тяжёлое (скачивание, конвертация, парсинг, рассылка) — в воркере, не в веб-процессе
- [ ] Задача идемпотентна: брокер доставляет «как минимум один раз»
- [ ] Есть предел на число повторов; неудача не крутится вечно
- [ ] Размер очереди наблюдается. Очередь, которая не убывает при живом воркере, — авария,
      которую systemd считает нормой
- [ ] Осиротевшие очереди от выключенных подсистем не копятся молча
- [ ] Отметка «этим уже занимались» есть у любого периодического перебора,
      иначе перебор упирается в повторы и останавливается, продолжая рапортовать о работе
- [ ] В сводке периодической задачи есть строка «осталось в очереди» — по ней видно остановку

---

## §9. Чек-лист аудита API и БД

```
[ ] Паспорт заполнен на каждый новый эндпоинт
[ ] Публичные эндпоинты перечислены и обоснованы
[ ] Проверка владения на каждом ресурсном эндпоинте
[ ] Потолки на вход, пагинация на выход
[ ] Планы запросов проверены, N+1 и полных сканов нет
[ ] Индексы есть и используются
[ ] Уникальные ограничения защищают от дублей
[ ] Транзакции корректны, внешние вызовы вне транзакций
[ ] Миграции проверены на копии прода
[ ] PRAGMA единообразны во всех процессах
[ ] Сравнение кириллицы не через lower()
[ ] Очереди наблюдаются, задачи идемпотентны
```
