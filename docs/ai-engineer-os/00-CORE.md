## §0. Установка режима

Работающий код ≠ хороший код.
Красивый интерфейс ≠ готовый продукт.
Отсутствие видимых ошибок ≠ безопасность.
Зелёные тесты ≠ production readiness.
`200 OK` ≠ операция выполнена корректно.

Разрабатывай так, будто система уже доступна из интернета реальным людям,
среди которых есть тот, кто хочет её сломать, и тот, кто нажмёт кнопку дважды.

## §1. Границы доверия

Недоверенные источники данных — **все** из списка:

- браузер и любой фронтенд (пользователь меняет его через DevTools);
- тело HTTP-запроса, query, заголовки, cookies;
- `initData`, deep-link, callback_data, любой апдейт Telegram;
- содержимое загруженных файлов, включая имя и MIME;
- ответы внешних сервисов (Telegram, ЮKassa, SoundCloud, YouTube, MusicBrainz);
- тексты, приехавшие из источников: названия треков, имена артистов, описания;
- **собственный код, написанный ранее.**

Доверенные: только то, что сервер вычислил сам из проверенных данных.

### Правило подстановки

Любой параметр, который влияет на права, деньги, доступ или объём работы,
**сервер обязан вычислить сам**, а не принять от клиента:

| Никогда не принимать от клиента | Как правильно |
|---|---|
| `user_id`, `telegram_id` | Взять из проверенного токена/сессии |
| `is_admin`, `role`, `is_premium` | Посчитать на сервере по БД |
| `price`, `amount`, `discount`, `months` | Взять из серверного справочника тарифов |
| `balance`, `days`, `count` | Посчитать по журналу операций |
| `path`, `filename`, `key` хранилища | Собрать из id ресурса |
| `limit`, `page_size` без потолка | Ограничить сверху константой |

Клиент может **попросить**. Решает сервер.

## §2. Классификация находок (severity)

| Уровень | Определение | Реакция |
|---|---|---|
| **CRITICAL** | Утечка чужих данных, обход авторизации, потеря денег, RCE, полная недоступность сервиса | Исправить немедленно, до любой другой работы. Деплой отдельным коммитом |
| **HIGH** | Эскалация прав в ограниченном контуре, потеря данных пользователя, обход бизнес-лимита, падение ключевого сценария | Исправить в этой же сессии |
| **MEDIUM** | Деградация под нагрузкой, отсутствие лимита, шумные логи, отсутствующий индекс, необработанное состояние UI | В план на ближайшую сессию, зафиксировать в `PROJECT-STATUS.md` |
| **LOW** | Читаемость, дублирование, мелкие несоответствия | По желанию владельца |
| **UNKNOWN** | Проверить не удалось (нет доступа, нет данных, нужен живой клиент) | Явно записать с причиной. **Не превращать в PASS** |

Каждая находка описывается по форме:

```
[SEVERITY] Что не так
Где: файл:строка
Как воспроизвести: конкретные входные данные / шаги
Последствие: что получит злоумышленник или что сломается
Исправление: что сделано
Тест: какой тест теперь это стережёт
```

Без «Как воспроизвести» находка не считается находкой — это догадка.
Догадки помечаются `ГИПОТЕЗА` и проверяются, а не докладываются как факт.

## §3. Порядок работы над задачей

### 3.1 До кода — модель системы

Ответить письменно (кратко, но ответить):

```
Кто действующие лица?           (гость, пользователь, премиум, админ, воркер, внешний сервис)
Какие ресурсы затрагиваются?    (данные, файлы, деньги, права)
Кто чем владеет?                (правило ownership для каждого ресурса)
Что критично?                   (что нельзя потерять, подделать, повторить)
Откуда приходят данные?         (границы доверия §1)
Что при ошибке?                 (частично выполненная операция — какое состояние)
Что при повторе?                (та же операция дважды — что должно произойти)
Что при 1000× нагрузке?         (где узкое место)
```

Если требование не сформулировано владельцем — **дописать его самому** и
сообщить. Недописанные требования — главный источник дыр.

Пример: «сделай донаты» подразумевает ещё и: повторный вебхук, отрицательная
сумма, чужая валюта, отмена платежа, рейтинг спонсоров и его накрутка, анонимность.

### 3.2 Модель угроз (для функции, где есть права, деньги или чужие данные)

```
Ресурс → Кто атакует → Точка входа → Граница доверия → Угроза → Последствие → Защита → Тест
```

Роли атакующего, которые нужно перебрать:
неавторизованный; обычный пользователь; пользователь, целящийся в чужой ресурс;
бот-скрипт; скомпрометированный внешний сервис; собственный админ по ошибке.

### 3.3 Реализация

- Безопасность встраивается в архитектуру, а не добавляется потом.
- Валидация — на сервере. Валидация на клиенте — только для удобства.
- Проверка прав — на каждом эндпоинте, а не в общем «мидлваре, который вроде есть».
- Ошибки — обрабатываются на границах; наружу не уходят трассировки и пути.
- Защитный механизм не удаляется ради упрощения. Если мешает — обсудить, не убирать молча.

## §4. Типовые провалы ИИ-кода

Подозревай **себя** в этом списке в первую очередь. Проверено практикой.

1. Пишет код, который выглядит правильно, и на этом останавливается.
2. Реализует только счастливый путь.
3. Доверяет фронтенду: берёт из запроса id пользователя, роль, цену.
4. Забывает проверку владения ресурсом (IDOR) — проверяет «существует ли», а не «твой ли».
5. Ставит авторизацию на «главные» эндпоинты и забывает на служебных.
6. Не думает о параллельных запросах и двойном нажатии.
7. Не делает операции идемпотентными: повторный вебхук создаёт вторую запись.
8. Глушит исключения так, что отказ становится неотличим от «ничего не найдено».
9. Смешивает «источник не ответил» и «источник ответил: ноль» в одно значение.
10. Кэширует отрицательный результат, полученный из-за сбоя.
11. Оставляет секрет в коде, в логе, в ответе API, в образе, в истории git.
12. Копирует небезопасный пример из документации библиотеки.
13. Считает `200 OK` доказательством, что операция выполнена.
14. Выдаёт наружу подробную ошибку с путями и SQL.
15. Не ставит лимит на объём: `page_size`, размер тела, длину строки, число элементов.
16. Делает тяжёлую работу внутри HTTP-запроса вместо очереди.
17. Ставит `Restart=always` на процесс, который падает при старте, — и получает генератор нагрузки вместо защиты.
18. Задаёт лимит памяти, не проверив, влезает ли в него сам процесс.
19. Пишет «исправлено» без теста, который бы поймал регресс.
20. Рапортует `PASS` там, где проверку не выполнял.

### Отдельно: два провала, специфичных для этого проекта

21. **Сравнение строк с кириллицей через `lower()`/`ilike` в SQLite.** SQLite
    понижает только ASCII. Любое сравнение с пользовательским текстом — через
    нормализованную в Python колонку. Этот баг здесь уже трижды стоил крови:
    поиск, привязка артистов, дедуп при импорте.
22. **Молчаливый отказ внешнего источника.** Прокси/узел/токен умирает, а код
    возвращает пустой результат — и это неотличимо от «ничего не найдено».
    Отказ обязан быть отличим от пустоты и обязан быть заметен (алерт).

## §5. Проходы самопроверки

После реализации выполнить проходы. Минимум обязательны **1, 2, 3, 5**.
Полный набор — перед релизом крупной функции и при аудите по запросу владельца.

| # | Проход | Главный вопрос | Что искать |
|---|---|---|---|
| 1 | **Функциональный** | Работает ли заявленное? | Счастливый путь + границы входных данных |
| 2 | **Авторизация** | Может ли это сделать другой пользователь? | IDOR, отсутствие проверки владения, служебные эндпоинты без прав |
| 3 | **Валидация и подделка** | Что если прислать мусор? | `null`, `{}`, `[]`, `""`, `0`, `-1`, огромные числа, чужие типы, гигантский JSON, кривой UTF-8 |
| 4 | **Злоупотребление** | Что если вызвать 10 000 раз? | Лимиты, стоимость запроса, усиление нагрузки, спам наружу |
| 5 | **Гонки и повторы** | Что при двух одновременных и при повторе? | Двойное начисление, дубль записи, потерянное обновление, неидемпотентный вебхук |
| 6 | **Отказы** | Что если БД/Redis/Telegram/платёжка недоступны? | Таймауты, повторы, деградация, fail-closed vs fail-open — осознанный выбор |
| 7 | **Производительность** | Что при 100× данных? | N+1, отсутствие индекса, полный скан, объём ответа, память |
| 8 | **Секреты и утечки** | Что видно наружу? | Токены в логах/ответах/образе, трассировки, внутренние пути, чужие id |
| 9 | **Поддерживаемость** | Сможет ли другой это изменить через год? | Инварианты проекта, слои, имена, мёртвый код |
| 10 | **Состязательный** | Куда я полез бы, если бы хотел сломать? | Целенаправленная попытка обойти всё выше |

### Формат отчёта прохода

```
ПРОХОД N — <название>
Область: какие файлы/эндпоинты просмотрены
Проверено: список конкретных проверок
Находки: по форме §2 (или «нет находок» — только если реально смотрел)
Не проверено: что и почему → UNKNOWN
```

## §6. Состязательный аудит (проход 10, развёрнуто)

Роль: у тебя есть обычный пользовательский аккаунт и браузер. Задача — сломать.
Перебрать каждый пункт и записать результат:

- Стать админом.
- Получить чужой профиль / библиотеку / плейлист / файл.
- Изменить чужие данные.
- Вызвать закрытый эндпоинт напрямую, минуя интерфейс.
- Подделать пользователя Telegram (`initData`, `user_id` в теле, старый токен).
- Переиспользовать перехваченный токен/подпись/ссылку.
- Изменить цену, срок, скидку, сумму платежа.
- Провести операцию дважды (кнопка, вебхук, задача в очереди).
- Обойти лимит: rate limit, лимит загрузок, лимит плейлистов, антифлуд.
- Вызвать гонку: два одновременных запроса на одно начисление.
- Залить вредоносный файл; подменить расширение/MIME; выйти из каталога хранилища.
- Вытащить секрет: из фронтенда, из ошибки, из лога, из ответа API.
- Уронить сервис дешёвым запросом (тяжёлый поиск, огромный `page_size`, гигантский JSON).
- Нарушить целостность БД: осиротить связи, обойти уникальность, испортить состояние.

Каждый пункт → `НЕ УДАЛОСЬ (почему)` / `УДАЛОСЬ → CRITICAL/HIGH + исправление` / `UNKNOWN`.

## §7. Гейт готовности

Функция считается готовой, когда все пункты дают `✓` или явный `UNKNOWN` с причиной:

```
[ ] Требования дописаны (в т.ч. неявные) и подтверждены
[ ] Права проверяются на сервере, на уровне ресурса
[ ] Все входные данные валидируются на сервере
[ ] Ошибки обработаны, наружу не уходит внутренняя информация
[ ] Повтор операции безопасен (идемпотентность там, где нужна)
[ ] Параллельные запросы безопасны
[ ] Есть лимиты (rate + бизнес-лимит — это разные механизмы)
[ ] Секреты не утекают
[ ] Тесты: счастливый путь + каждая найденная дыра
[ ] Логи: событие видно; секретов в логах нет
[ ] Деградация при отказе зависимостей описана и проверена
[ ] Инварианты проекта из CLAUDE.md не нарушены
[ ] PROJECT-STATUS.md обновлён
[ ] Новые уроки внесены в LESSONS.md
```

## §8. Право сказать «не знаю»

Если неизвестно: актуальная версия API, поведение библиотеки, юридическое
требование, состояние прода, содержимое чужого устройства —

1. назвать неизвестное явно;
2. проверить по первоисточнику (документация, живой замер на проде, вопрос владельцу);
3. **не выдумывать**;
4. если проверить нельзя — `UNKNOWN` с причиной.

Замер на проде важнее рассуждения. Рассуждение о том, что «должно работать»,
уже несколько раз в этом проекте оказывалось неверным: мёртвые прокси,
неработающий дедуп, остановленные воркеры — всё выглядело исправным.

## §9. Цикл накопления знаний

Каждый инцидент и каждая дыра проходят через `LESSONS.md`:

```
Симптом
  ↓
Корневая причина (не «сломалось», а почему сломалось)
  ↓
Почему ИИ это допустил — какой принцип нарушен
  ↓
Универсальное правило (годится для любого проекта)
  ↓
Тест, который поймает регресс
  ↓
Пункт в чек-лист соответствующего модуля
```

Правило без теста забудется. Тест без правила не переносится на другие места.
Нужны оба.
