## Находки этого прохода

### [HIGH] Журнал выручки не идемпотентен — повторный вебхук удваивает платёж

**Где:** [app/services/revenue.py:18](../../app/services/revenue.py#L18) `record_payment`,
модель `Payment` — [app/db/models.py:297](../../app/db/models.py#L297)

**Суть.** `record_payment` вставляет строку безусловно. У `Payment.charge_id`
нет ни проверки на существующий, ни уникального индекса. ЮKassa повторяет
уведомление, пока не получит `200`, — повтор по уже обработанному платежу
добавит вторую строку в журнал.

**Как воспроизвести:** доставить `payment.succeeded` по одному и тому же
`payment_id` дважды в ситуации, когда защита выше по стеку не сработала (см.
следующую находку) — в `payments` появятся две записи на один платёж.

**Последствие:** завышенная выручка в админ-статистике. Деньги не теряются, но
отчёт врёт, а именно по нему принимаются решения.

**Показательно:** в соседней, более новой таблице `Donation` ровно этот урок уже
учтён — `payment_id` объявлен `unique` с комментарием «ключ идемпотентности».
В `payments` его не добавили.

**Исправление: ✅ применено.**
1. Проверен прод: в `payments` **0 строк**, дублей по `charge_id` — 0, значит
   уникальный индекс встаёт на чистых данных.
2. `record_payment` дедуплицирует по `charge_id` и возвращает `bool`.
3. Миграция `a1b2c3d4e5f8` — частичный уникальный индекс `ux_payments_charge_id`
   (только для непустого `charge_id`: у Stars он пуст). Проверена `upgrade` и
   `downgrade` на временной БД.
4. Тесты: [tests/test_payment_idempotency.py](../../tests/test_payment_idempotency.py).

⚠️ Уникальность именно в БД, а не только проверка в коде: повторы приходят
параллельно, и «проверил → вставил» между двумя обработчиками не защищает.

### [HIGH] Идемпотентность активации Premium ломается при двух платежах подряд

**Где:** [app/services/yookassa_payments.py:230](../../app/services/yookassa_payments.py#L230)

```python
subscription = await session.get(PremiumSubscription, user.id)
if subscription is not None and subscription.payment_id == payment["id"]:
    return True  # повторное уведомление — уже обработано
```

**Суть.** Защита от повтора смотрит только на **последний** платёж пользователя.
Она перестаёт работать, как только пришёл следующий.

**Как воспроизвести:**
1. Пользователь оплачивает 1 месяц — платёж `A`. Вебхук `A` обработан,
   `subscription.payment_id = A`.
2. Тот же пользователь оплачивает 12 месяцев — платёж `B`. Теперь
   `subscription.payment_id = B`.
3. ЮKassa повторно доставляет уведомление по `A` (повторы идут до успешного
   ответа, окно — часы).
4. Условие `payment_id == A` ложно → `activate_premium` вызывается **второй раз**
   по платежу `A`: пользователь получает лишний месяц, в журнал выручки
   ложится дубль.

**Последствие:** выдача оплаченного товара сверх оплаченного + искажение отчёта.
Это не кража у пользователя, а потеря на стороне сервиса.

**Правильная защита:** ключ идемпотентности — **сам факт «этот `payment_id` уже
применён»**, а не сравнение с текущим состоянием. То есть та же таблица-журнал с
уникальным `charge_id`: если вставка отбита уникальностью — операция уже была,
выходим. Это чинит обе находки одной правкой.

**Исправление: ✅ применено.** Идемпотентность переведена на журнал платежей
(`payment_already_recorded`). Прежняя проверка по состоянию подписки оставлена
**вторым рубежом** — для платежей, применённых до появления журнала: у них
строки в `payments` нет, и по одному журналу повтор был бы не виден.
Тест `test_replay_after_second_payment_does_not_grant_twice` воспроизводит
именно сценарий A → B → повтор A.

### [MEDIUM] Копейки отбрасываются при записи в журнал

**Где:** `apply_succeeded_payment` и `_apply_donation`, `int(float(amount_raw))`.

Сумма приходит строкой вида `"78.00"` и приводится к целому рублю усечением.
Для текущих тарифов (целые рубли) расхождения нет, но правило из
[05-PAYMENTS §4](05-PAYMENTS.md) нарушено: журнал денег должен быть точным.
При появлении нецелых сумм отчёт начнёт занижать выручку молча.

**Исправление: ✅ применено.** Введена `_amount_to_rub`: округление вместо
усечения плюс предупреждение в журнал, если сумма нецелая — это сигнал, что
появился тариф, под который журнал не рассчитан. Перевод журнала на копейки не
делался: все текущие суммы целые, и менять схему ради гипотетического случая
дороже, чем поймать его предупреждением.

## Что проверено и оказалось исправным

Не перепроверять без причины.

### initData — соответствует документации Telegram

[app/api/security.py](../../app/api/security.py) реализует ровно документированный
алгоритм: `secret_key = HMAC_SHA256("WebAppData", bot_token)`, `data_check_string`
из отсортированных полей через `\n`, сравнение через `compare_digest`.
**Свежесть `auth_date` проверяется после подписи** — порядок верный, на него есть
тест. Отсутствие `hash` → отказ. `PASS` по [04-TELEGRAM §1](04-TELEGRAM.md).

### Авторизация эндпоинтов

Из 60 эндпоинтов без зависимости `get_current_user` остаются 4, и каждый —
осознанно:

| Эндпоинт | Чем защищён |
|---|---|
| `POST /login` | точка входа, проверяет `initData` |
| `GET /tracks/{id}/audio` | HMAC-подпись ссылки со сроком |
| `GET /instrumentals/{id}/audio` | HMAC-подпись, **отдельное пространство имён** (подпись трека не подходит) |
| `GET /stream/{ref}` | подписанный ref со сроком |
| `POST /webhook/yookassa` | перепроверяет платёж запросом к API ЮKassa |

Роутер `catalog` закрыт зависимостью на уровне роутера
(`APIRouter(dependencies=[Depends(get_current_user)])`) — при беглом чтении
выглядит как «эндпоинты без авторизации», но это не так.

⚠️ Уточнение к записи в CLAUDE.md: там сказано «у всех эндпоинтов есть
`Depends(get_current_user)` — кроме вебхука». Точнее: **кроме вебхука и трёх
эндпоинтов выдачи медиа**, которые защищены подписью, а не токеном.

### Вебхук платежей

Телу уведомления не доверяют — статус перепроверяется у API ЮKassa.
Возврат (`refund.succeeded`) разбирается корректно: `object.id` — id возврата,
платёж берётся из `object.payment_id`, и он тоже перепроверяется.
Донат отделён от Premium меткой `metadata.kind` **до** любой ветки активации.

### Идемпотентность донатов

`Donation.payment_id` — `unique`, `record_donation` возвращает `None` на повторе.
Соответствует [05-PAYMENTS §3](05-PAYMENTS.md).

### Лимит частоты у API

`RateLimitMiddleware` подключён в [app/api/app.py](../../app/api/app.py).
Прежняя запись «у API лимитера нет» устарела.

### Потолок страницы

`page_size` ограничен сверху (`MINIAPP_MAX_PAGE_SIZE = 100`) в каталоге.

## Открытые вопросы юридического слоя

1. **Уведомление регулятора об обработке персональных данных.** Сервис собирает
   данные пользователей Telegram и принимает деньги через российскую платёжную
   систему. С 30 мая 2025 года за неуведомление предусмотрен штраф, в том числе
   для самозанятых. Статус: **не подтверждено, что уведомление подано.**
   Это вопрос к владельцу, а не к коду.

2. **Основание для раздачи каталога.** Для музыкального сервиса это главный
   юридический риск — больше, чем персональные данные. Нужны: канал для
   обращений правообладателей, срок реакции, техническая возможность быстро снять
   объект. Статус: **не проработано.**
   Отдельно: при переезде на западную платёжную систему её требования к товару
   строже закона — подтверждать **до** переезда, иначе обслуживание не откроют.

3. **Переезд на `.com` и западную аудиторию** (решение владельца).
   Юрисдикция определяется аудиторией, получателем денег, сервером и контентом,
   а не зоной домена — см. [07-LEGAL §1](07-LEGAL.md). Чек-лист переезда — §7 того
   же файла. Прежние обязанности нужно закрыть, а не оставить.
