# Живой поиск вместо каталога

**Дата:** 2026-08-02
**Статус:** одобрено владельцем заранее, реализуется в этой же сессии

## Зачем

Массовый парсер на 1 млн треков выключен с 27.07: сервер 961 МБ RAM его не тянет,
дважды ронял прод. Но поиск при этом остался устроен «по каталогу»: бот ищет по
локальной базе (~30k треков), и только если она вернула **ноль** строк — идёт в сеть.
На практике локальный поиск по подстроке почти всегда что-то возвращает, поэтому
живой поиск не срабатывает, а пользователь видит пять похожих мусорных совпадений
вместо нужного трека. Отсюда жалоба владельца: «поиск слабый, мало треков,
андеграунд не находится».

Решение владельца: **каталог не копим, ищем сразу в источниках**. Поиск —
главная фича продукта; он должен работать одинаково в боте и в Mini App.

## Решения владельца (зафиксировано)

| Вопрос | Решение |
|---|---|
| Выдача | Список кандидатов из сети, а не один «лучший» трек |
| Локальная база в поиске | Не используется — ищем сразу в источниках |
| Источники | SoundCloud приоритетный и берётся целиком; YouTube добавляет только то, чего в SC нет |
| Хранение найденного | Метаданные + Telegram `file_id`. Ни отпечатков, ни архивных копий на диске |
| Старый каталог | Удалить только явный шлак по критериям; остальные строки не трогать |
| Mini App | Играет потоком сразу, скачивание и заливка в Telegram — фоном |
| Микс и «настроения» | Сид-запросы к SoundCloud + история прослушиваний. Каталог не нужен |
| Деньги | Поиск бесплатный (воронка), плеер и миксы — Premium 29 ₽ |
| Компромисс охват/чистота | Охват. Пропустить нужный трек хуже, чем показать лишний |

Каталог вернётся, когда появится мощный VPS — тогда массовый парсер и PostgreSQL
включаются обратно. Эта спека не должна закрывать такую возможность: код
массового парсера остаётся рабочим, меняется только путь поиска.

## Архитектура

```
запрос «кизару фейк айди»
   │
   ├─► SoundCloud  scsearch{N}  ─┐  параллельно (asyncio.gather поверх to_thread)
   └─► YouTube     ytsearch{N}  ─┘  отказ одного источника не роняет второй
                    ▼
            merge_candidates(sc, yt)
              SC идёт первым и целиком
              YouTube добавляет только то, чего нет в SC
              дедуп по нормализованному «артист + название» (транслит)
                    ▼
            кэш выдачи: Redis, TTL 3 ч, ключ — нормализованный запрос
                    ▼
      ┌─────────────┴──────────────┐
    БОТ                          MINI APP
    кнопки по индексу             карточки + подписанный ref
    кандидаты в FSM               GET /search/live
    тап → скачать → аудио         тап → GET /stream/{ref} играет сразу
                                        фоном: скачать → минт → file_id
```

### Новые модули

| Модуль | Ответственность |
|---|---|
| `services/track_lookup/merge.py` | склейка источников и дедуп. Чистая функция, без сети |
| `services/search_cache.py` | кэш выдачи в Redis, graceful-фолбэк если Redis недоступен |
| `services/candidate_ref.py` | подписанный самодостаточный ref кандидата для Mini App |
| `services/stream_url.py` | резолв прямой ссылки на аудио через yt-dlp без скачивания |
| `api/routers/live_search.py` | `GET /search/live`, `GET /stream/{ref}`, `/shelves*`, фоновая заливка |
| `services/shelves.py` | полки «настроений» из сид-запросов + артисты из истории юзера |
| `cli/cleanup_catalog.py` | чистка каталога по критериям, по умолчанию — предпросмотр |

### Что меняется в существующем

- `track_lookup/providers.py` — кандидаты получают обложку и длительность; поиск
  обоих источников уходит параллельно.
- `track_lookup/__init__.py` — появляется `search_candidates()` (список).
  `find_track()` (один лучший) остаётся: им пользуется импорт по ссылке.
- `handlers/quick_search.py` — сеть становится основным путём, локальная база из
  поиска уходит.
- `keyboards/quick_search.py` — `callback_data` ссылается на индекс кандидата в
  FSM, а не на `track_id` (ссылка SoundCloud не влезает в 64 байта Telegram).
- `config.py` — `search_min_seconds: 60 → 0` (охват: фристайлы, интерлюдии и скиты
  короче минуты — это ровно андеграунд). Верхний порог 900 сек остаётся: часовые
  миксы и подкасты не нужны.

### Почему кандидаты не пишутся в базу

Записывать всех показанных кандидатов строками — значит растить базу от
**показов**, а не от прослушиваний: один запрос «кизару» = 8 мусорных строк.
Поэтому выдача живёт вне БД, а строка появляется в момент, когда трек реально
отдан пользователю и Telegram вернул `file_id`.

Ссылка на кандидата разная по транспортам, и это не костыль, а разница
транспортов: Telegram даёт под `callback_data` 64 байта — ссылка SoundCloud одна
съедает больше, поэтому в боте кандидаты лежат в FSM (там уже так хранится
запрос), а в Mini App JSON не ограничен и ref self-contained с HMAC-подписью
по образцу существующего `verify_audio_signature`.

## Поток данных при выборе трека

**Бот.** Тап → индекс → кандидат из FSM. Если такой трек уже есть в базе по
«артист+название» — отдаём мгновенно по `file_id`, ничего не качаем. Иначе задача
`search.fetch_candidate` уходит в очередь `youtube_user`, и уже воркер качает,
минтит и присылает аудио. Скачивание живёт в воркере намеренно: mp3 плюс
перекодирование ffmpeg — десятки мегабайт пиковой памяти, а бокс на 961 МБ
дважды ронял прод по OOM.

**Mini App.** Тап → `GET /stream/{ref}` отдаёт поток: резолвим прямую ссылку
источника через yt-dlp (`download=False`, берём URL формата) и проксируем байты с
поддержкой `Range`. Параллельно ставится Celery-задача заливки. Как только она
прошла — трек существует строкой и дальше играет мгновенно по `file_id` у всех.

Прямые ссылки SoundCloud живут ограниченное время, поэтому резолв URL кэшируется
на 10 минут, а не на 3 часа: устаревшая ссылка ломает воспроизведение, устаревшая
поисковая выдача — нет.

## Ошибки

- Источник не ответил → его кандидаты пустые, второй источник работает. Оба молчат
  → «Ничего не нашли» с подсказкой уточнить исполнителя.
- Redis недоступен → кэш пропускается, поиск идёт вживую. Кэш ускоряет, не блокирует.
- Ссылка потока протухла → `/stream` резолвит заново один раз, потом 404.
- `download_candidate` вернул None → пользователю честное «не получилось скачать»,
  кандидат в выдаче остаётся, можно выбрать соседний.
- Диск почти полон → работает существующий `enough_free_disk`: скачивание
  пропускается, поток в Mini App всё равно играет (он ничего не пишет на диск).

## Чистка старого каталога

Удаляются **полностью** (строка + связи + файл) только по явным критериям:
клипы и видео по маркерам названия, треки длиннее 15 минут, треки без обложки.
Отдельно удаляются архивные копии с диска и индекс отпечатков — они нужны были
массовому парсеру для дедупа, а живому поиску не нужны и стоят 128 МБ индекса
плюс гигабайты диска.

Библиотеки и плейлисты уцелевших треков не трогаются: строка «артист + название +
file_id» весит ~200 байт и остаётся источником истины для того, что люди уже
слушали.

## Тесты

Чистая логика (без сети) покрывается юнит-тестами:
- `merge_candidates`: SC целиком; YouTube-дубликат отбрасывается; YouTube-уникальный
  добавляется; дедуп срабатывает через транслит («Kizaru — Fake ID» ↔ «кизару фейк айди»).
- `candidate_ref`: подпись сходится, чужая подпись отвергается, протухшая отвергается.
- `shelves`: сид-запросы перемешиваются без повторов, история юзера подмешивается.
- `search_cache`: отсутствие Redis не роняет поиск.

Сеть проверяется вживую на VPS через CLI после деплоя.

## Инварианты

- Кандидат поиска не пишется в `tracks` до того, как трек реально отдан.
- `services/` не импортируют aiogram (кроме уже существующих исключений с минтом).
- SoundCloud всегда выше YouTube при равном совпадении.
- Живой поиск не зависит от Redis: кэш — ускорение, не требование.
- Массовый парсер и `find_track` остаются рабочими — каталог вернётся на новом VPS.
